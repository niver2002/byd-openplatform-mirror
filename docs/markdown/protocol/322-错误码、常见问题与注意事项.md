# 错误码、常见问题与注意事项

> 来源：软件开发协议 / 直连接入协议 / 比亚迪智能设备开放接入协议 / 错误码、常见问题与注意事项 · https://openplatform.byd.com/#/document/index?id=322

## **错误码、常见问题与注意事项**

### **1. 错误码 （统一TLV格式）**

错误码采用 TLV（Type-Length-Value）分类体系，与 BLE 通用加密协议的ERROR 帧（Opcode 0x20FF）格式对齐。JSON 层通过 err 数组承载 TLV 错误信息，天然提供长度语义，故 L 省略。

#### **1.1 错误响应格式**

成功响应保持 "code": 0。错误响应通过 err 数组携带 TLV 错误详情，支持同时返回多种类型错误（如同时返回语音 TTS + 加密错误，对应 BLE ERROR 帧中多个TLV 共存）：

成功：

```
JSON
{"mid": "1", "code": 0, "v": "42"}
```

错误（单一类型）：

```
JSON
{"mid": "2", "code": -1, "err": [{"t": 2, "v": "1"}], "msg":"签名验证失败"}
```

错误（多类型同时返回 — 语音 TTS + 加密错误）：

```
JSON
{"mid": "3", "code": -1, "err": [{"t": 1, "v": "2"}, {"t":2, "v": "1"}], "msg": "签名验证失败"}
```

|  |  |
|---|---|
| 字段 | 说明 |
| code | 0 = 成功；-1 = 失败（详见 err）；1–9= 通用协议错误（兼容旧版，见本文1.8） |
| err | TLV 错误数组，每个元素 {"t": <类型>, "v": <错误值>}；t 为原生整数，v 为字符串；可包含多个不同类型 |
| msg | 可选，人类可读的错误描述 |

#### **1.2 错误码 Type 定义**

|  |  |  |  |  |
|---|---|---|---|---|
| Type (t) | 名称 | 长度 | 用途 | BLE TLV Tag |
| 0x01 | VOICE_ERROR | 1B | 语音反馈码，供语音 TTS播报及业务命令执行结果反馈使用；任何需要向用户传达执行结果的场景均可使用（与 BLE 传输层错误不同，属于应用层反馈） | 0x01 |
| 0x02 | CRYPTO_ERROR | 1B | 加密协议错误码，供安全通信使用 | 0x02 |
| 0x03 | FTX_ERROR | 1B | 文件传输错误码 | 0x03 |
| 0x04 | OTA_ERROR | 1B | OTA 升级错误码 | 0x04 |

#### **1.3 T=0x01 语音反馈码（VOICE_ERROR）**

**重点说明**：VOICE_ERROR（t:1）是应用层语音反馈通道，为语音 TTS 播报提供反馈信息。t:1 不全是"错误"——如 0x00=执行成功、0x03=重复指令（已是目标状态）都不是错误，本质上是让语音模块能向用户做出恰当回应。与 BLE 传输层错误（如BluetoothGattCallback 中的连接断开、GATT 内部错误等）属于不同层级。传输层错误由车机协议栈自动处理；而 t:1 由设备端业务逻辑主动返回，车机提取后触发 TTS播报或 UI 状态更新。支持语音控制的设备（如儿童座椅、宠物笼、停车牌等）必须实现本节全部反馈码。

|  |  |  |  |
|---|---|---|---|
| Value (v) | 名称 | 含义 | TTS 播报 |
| 2 | EXECUTE_FAIL | 执行失败 | "抱歉，操作失败了，请稍后再试" |
| 3 | INSTRUCTION_REPEAT | 重复指令（已是目标状态） | "已经是这个状态了呢" |
| 4 | LOW_BATTERY | 低电不执行 | "当前设备电量低，无法执行操作" |
| 5 | UNSUPPORTED | 指令不支持 | "抱歉，不支持该指令" |
| 6 | CONDITION_NOT_MET | 条件不满足 | "抱歉，执行条件不满足" |
| 7 | INVALID_PARAM | 非法参数（超出范围） | "抱歉，超出设置范围了" |
| 8 | DEVICE_OFFLINE | 设备未开机/离线 | "当前设备未开机" |
| 9 | UNIT_MISMATCH | 单位不匹配 |  |

**用法**：业务命令执行后，设备通过 err:[{"t":1, "v":"<code>"}] 返回语音反馈码，网关/车机提取后触发对应 TTS 播报或 UI 状态更新。当 Profile 声明$meta.voice_feedback: true 时，网关将 t:1 视为语音反馈通道，不上透给App，仅触发 TTS 播报；code 仍正常透传（如 code:0 表示 BLE 写入成功，附带 err 仅为语音 TTS 提供反馈）。

**业务执行错误码使用示例：**

```
# 语音控制风扇 — 执行成功
车机→设备: {"mid": "1", "op": "w", "srv": "stat", "chr":"fan_mode", "v": "2"}
设备→车机: {"mid": "1", "code": 0}TTS 播报: "好的，已打开儿童座椅通风"

# 语音控制风扇 — 低电不执行
车机→设备: {"mid": "2", "op": "w", "srv": "stat", "chr":"fan_mode", "v": "2"}
设备→车机: {"mid": "2", "code": -1, "err": [{"t": 1, "v":"4"}], "msg": "low battery"}
TTS 播报: "当前设备电量低，无法执行操作"

# 语音控制旋转 — 重复指令（已是目标状态）
车机→设备: {"mid": "3", "op": "w", "srv": "action", "chr":"rotate", "v": "1"}
设备→车机: {"mid": "3", "code": -1, "err": [{"t": 1, "v":"3"}]}
TTS 播报: "已经是这个状态了呢"
说明: BLE 写入成功（设备已处于目标状态），附带语音反馈码供 TTS 播报

# 语音控制俯仰 — 角度已最大
车机→设备: {"mid": "4", "op": "w", "srv": "action", "chr":"tilt_cmd", "in": {"action": "forward"}}
设备→车机: {"mid": "4", "code": -1, "err": [{"t": 1, "v":"6"}]}
TTS 播报: "抱歉，执行条件不满足"

# 语音查询不支持的功能
车机→设备: {"mid": "5", "op": "w", "srv": "stat", "chr":"unsupported_feature", "v": "1"}
设备→车机: {"mid": "5", "code": -1, "err": [{"t": 1, "v":"5"}]}
TTS 播报: "抱歉，不支持该指令"

# 同时返回业务执行错误 + 加密错误
设备→车机: {"mid": "6", "code": -1, "err": [{"t": 1, "v":"2"}, {"t": 2, "v": "5"}], "msg": "handshake incomplete"}
```

#### **1.4 T=0x02 加密协议错误码（CRYPTO_ERROR）**

加密协议错误码覆盖签名验证、密钥交换、加密通信等安全相关场景，共 10 个错误码（0x01–0x09 + 0xFF），详见 《AutoIoT 安全服务技术实现》第 9 章。

#### **1.5 T=0x03 文件传输错误码（FTX_ERROR）**

文件传输错误码覆盖帧格式校验、资源限制、解密失败等场景，共 6 个错误码（0x01–0x05 + 0xFF），详见 《AutoIoT 文件传输技术实现》第 8 章。

#### **1.6 T=0x04 OTA 升级错误码（OTA_ERROR）**

OTA 升级错误码覆盖设备状态、下载、校验、安装等场景，共 16 个错误码（0x00–0x0D + 0x7F + 0x80），详见 《AutoIoT OTA 升级技术实现》第 11 章。

#### **1.7 错误码优先级规则**

当 err 数组存在时，以 err 为准；err 不存在且 code 为 1–9 → 按通用协议错误处理（见本文1.8）。

当 err 包含多种类型时，处理规则如下：

|  |  |  |
|---|---|---|
| 优先级 | 处理方式 | 说明 |
| 最高 | TTS 播报 | 若 t:1 存在，提取VOICE_ERROR 触发TTS |
| 其次 | 安全处理 | 若 t:2 存在，提取CRYPTO_ERROR 触发安全流程处理 |
| 最后 | 业务记录 | 若 t:3 / t:4 存在，记录日志 / 更新 UI 状态 |

#### **1.8 通用协议错误码（兼容旧版）**

当 err 数组不存在且 code 为 1–9 时，按以下通用协议错误处理（兼容旧版设备）：

|  |  |
|---|---|
| code | 含义 |
| 1 | 通用错误（未知原因） |
| 2 | 协议格式错误 |
| 3 | 设备不支持该操作 |
| 4 | 参数不合法 |
| 5 | 设备内部错误 |
| 6 | 资源不足 |
| 7 | 超时 |
| 8 | 设备忙碌 |
| 9 | 权限不足 |

新设备应优先使用 TLV err 数组（code: -1），通用协议错误码仅用于兼容不支持TLV 的旧版设备。

### **2. 常见问题与注意事项**

#### **2.1 数值为何采用字符串表示？**

A：为与云家电物模型对齐，数值统一用字符串表示。接收端需持有 Profile Schema（f 类型信息）才能正确反序列化。CBOR 编码下数值仍使用原生类型。

#### **2.2 安全等级选择错误如何处理？**

A：

• 选用 S2 但设备未烧录长期密钥 → 握手失败，需重新烧录密钥。

• 选用 S0 但设备为门锁等高风险设备 → 安全性不足，建议升级至 S2。

• 等级选择不确定时 → 建议先选用 S1，后续按需求升级。

#### **2.3 Profile 体积过大如何优化？**

A：

• 先查询摘要（$prof.$digest），比对版本号，版本一致则使用缓存。

• 必须拉取时自动启用分片机制。

• 建议采用 CBOR 编码，可减少分片数量一半以上。

#### **2.4 分片传输中断如何处理？**

A：

• 单片超时（建议 5s）→ 接收端丢弃重组缓冲区

• 重试超过 3 次 → 发送端放弃本次传输

• 重新开始传输 → 使用新的 frag_id

#### **2.5 OTA 升级失败常见原因？**

A：

• 电量不足（ota_cap 返回 0）

• 设备正在使用（返回 OTA_DEVICE_BUSY）

• 固件校验失败（checksum 不匹配）

• Flash 空间不足

#### **2.6 设备广播未被扫描到的可能原因？**

A：

• 广播间隔过长（建议 20-100ms）

• 广播包格式错误（检查 0xFF 字段）

• 设备名称包含特殊字符或过长

#### **2.7 业务执行错误码和 BLE 传输层错误的关系？**

A：t:1（VOICE_ERROR）属于应用层语音反馈码，与 BLE 传输层错误（如BluetoothGattCallback 中的连接断开、GATT 内部错误）属于不同层级：

• 传输层错误：由车机 BLE 协议栈自动处理（如断链重连），设备不感知，不在err 数组中体现。

• t:1 语音反馈码：由设备端业务逻辑主动返回，为语音 TTS 提供反馈信息；t:1不全是"错误"——如 0x03=重复指令表示 BLE 写入成功但设备已是目标状态，code:0 + err 共存时 code 表示 BLE 通信结果，err 为语音通道附加信息。

• 支持语音控制的设备必须实现完整 VOICE_ERROR 反馈码表（0x00–0x08），确保每种执行结果都有对应 TTS 播报。

• 不支持语音但需要执行结果反馈的设备，也可通过 t:1 返回反馈码，车机侧可选择仅更新 UI 状态而不触发 TTS。

• 当 Profile 声明 $meta.voice_feedback: true 时，网关将 t:1 视为语音反馈通道，不上透给上层 App，仅触发 TTS 播报。

#### **2.8 err 数组包含多种类型时如何处理？**

A：按优先级分层处理：

• t:1（VOICE_ERROR）→ 优先触发 TTS 播报，面向用户反馈。

• t:2（CRYPTO_ERROR）→ 触发安全流程处理（如断开连接、重新握手）。

• t:3 / t:4（FTX_ERROR / OTA_ERROR）→ 记录日志、更新 UI 状态。

• stat：状态服务，包含开关、温度、风扇模式等可读写字段。

• btry：电池服务，上报电量状态。

• ota：OTA 服务，声明设备支持 OTA 升级，并给出帧大小、分区、命令和进度特征
