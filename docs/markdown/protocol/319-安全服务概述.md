## **安全服务概述**

### **1. 安全等级对比**

|  |  |  |  |  |
|---|---|---|---|---|
| 等级 | 标识 | 加密 | 身份验证 | 适用场景 |
| S0 | none | 无 | 无 | 调试、演示 |
| S1 | ecdh_only | AES-GCM | 临时签名 | 部分 BLE 可车控设备 |
| S2 | ecdh_auth | AES-GCM | 后端验证身份后进入 S1 流程 | 门锁、支付设备 |
| S3 | custom_auth | AES-GCM | 厂商自定义验证 | 特殊场景 |

### **2. 握手流程概览**

安全握手分三步完成（S1 和 S2 共用结构，S2 多了身份验证）：

**前置条件**：车机必须（MUST）已完成服务发现、MTU 协商、Notify 订阅，并已通过缓存或 5.4 Profile 查询 确认本次连接的 sec.sec_lvl 与 init_pipeline。未满足这些条件前，不得发送 sec.init。

```
Step 1: 车机发起握手
→ 发送 nonce_gw + pub_gw_eph（临时公钥） + gw_id + ts

Step 2: 设备响应
→ 返回 nonce_dev + sn + pid + pub_dev_eph + sig_dev + ts
→ S2 还返回 pub_dev（长期公钥）用于后端验证

Step 3: 车机确认
→ 发送 result（成功/失败）
→ S2 还发送 sig_gw（网关签名）完成双向认证
```

握手成功后，双方派生会话密钥 k_enc，后续业务消息通过$sec 进行 AES-GCM 加密。

**补充规则**：

• handshake_mode 支持 auto / manual：auto 由中间件在 BLE 连接后自动发起握手；manual 由上层 App 显式触发。

• S2 可通过 backend_policy 声明后端不可达时的行为：strict（默认，直接失败）或 cache（允许使用本地缓存的注册结果）。

• S3 会在标准三步握手之前插入厂商自定义验证阶段；验证通过后再进入标准ECDH 握手。

• 若本次连接要求安全握手，则在 sess_state 建立前，除 sec 服务和init_pipeline 内声明的初始化步骤外，其他业务通信一律禁止（MUST NOT）发送、执行或上报。

• handshake_mode:"manual" 不表示可以先进入业务面再补做安全；它只表示由上层 App 触发 sec.init，业务放行时机仍以握手成功为准。
