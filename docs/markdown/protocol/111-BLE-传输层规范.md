# BLE 传输层规范

> 来源：软件开发协议 / 直连接入协议 / 比亚迪智能设备开放接入协议 / BLE 传输层规范 · https://openplatform.byd.com/#/document/index?id=111

## **BLE 传输层规范**

这一章讲的是 BLE 传输层的基本规则——设备怎么广播、怎么被发现、怎么建立连接。

可以把 BLE 传输理解为"设备的见面流程"：广播就是设备的简历，车机扫描到后主动握手，建立连接后开始聊业务。

### **1. 广播包设计**

设备通过 BLE 广播向车机声明设备身份和类型信息，车机扫描广播包后决定是否发起连接。广播包的核心字段为 **AD Type 0xFF（Manufacturer Specific Data）**，承载比亚迪自定义数据。

#### **1.1 广播包基本要求**

|  |  |  |  |
|---|---|---|---|
| AD Type | 名称 | 必须 | 说明 |
| 0x01 | Flags | 必须 | BLE 模式标志（通常 0x06） |
| 0x09 | Name | 必须 | 设备蓝牙名称 |
| 0xFF | Manufacturer Specific Data | 必须 | 比亚迪自定义数据（核心字段） |

#### **1.2 0xFF 字段格式**

0xFF 字段采用 TLV 结构，包含以下关键信息：

|  |  |  |  |
|---|---|---|---|
| Tag | 值 | 后续长度 | 含义 |
| 0x01 | 版本号 | 1B | 广播协议版本 |
| 0x02 | 设备类型 | 2B | 设备品类标识 |
| 0x03 | 设备模型 | 3B | 平台分配的模型 ID |
| 0x0C | 唯一标识 | 6B | 设备唯一标识（MAC/SN） |

注意：

• model_id 是平台分配的，厂商不能自己定义，要在【[比亚迪生态开放平台-管理中心-AIoT服务平台-产品接入-产品管理](#/product/productList)】新增产品的流程节点中申请。

• unique_id 通常是设备的 BLE MAC 地址，用于区分同型号的不同设备个体。

#### **1.3 广播示例**

```
# 完整 0xFF AD Structure（hex dump）
# Len Type CompanyID(LE) VerTag Ver DevTypeTag DevTypeModelTag ModelID UIDTag UniqueID
13     FF     34 0C     01     01 02      01 07     03      00 00 14      0C     11 22 33 44 55 66
```

解析结果：

• Company ID = 0x0C34（比亚迪）

• 协议版本 = 0x01（v1.0）

• 设备类型 = 0x0107

• 模型 ID = 0x000014（平台分配）

• 唯一标识 = 11:22:33:44:55:66（MAC 地址）

广播间隔建议：20ms~100ms 之间，太长会影响车机扫描成功率。

### **2. GATT 服务与特性**

建立连接后，车机通过 GATT 协议发现设备的服务和特性。

#### **2.1. 核心 GATT 服务**

|  |  |  |
|---|---|---|
| Service UUID | 名称 | 用途 |
| 0000300E-427D-EE7D-6974-7DC1FA381C06 | Event Service | 承载消息交互的读写通道 |

#### **2.2. 核心 GATT 特性**

|  |  |  |  |
|---|---|---|---|
| 特性名称 | UUID | 权限 | 用途 |
| Request (CBOR) | 00000023-427D-EE7D-6974-7DC1FA381C06 | Write 、Write without response | 车机→设备：CBOR消息写入通道（二进制更紧凑） |
| Response (CBOR) | 00000024-427D-EE7D-6974-7DC1FA381C06 | Notify | 设备→车机：CBOR消息通知通道 |

**编码说明：**统一使用 CBOR 编码，相比 JSON 更紧凑，省带宽。

### **3.  连接与MTU协商**

MTU（Maximum Transmission Unit）决定单次传输数据量上限。BLE 默认 MTU 仅23 字节，无法承载完整 JSON 消息，因此需要协商更大的 MTU 值。

|  |  |
|---|---|
| 项目 | 建议 |
| MTU 大小 | 车机主动发起 MTU Exchange 请求 512字节 |
| 连接间隔 | 最小 20ms，最大 45ms |
| 单条消息超过 MTU | 启用分片机制（见第 7 章） |

### **4.  连接初始化与业务就绪**

BLE 物理连接建立后，车机必须（MUST）作为 GATT 主控方推进连接初始化流程；设备作为从设备按车机节奏响应。连接初始化的目标是：在进入业务交互之前，先完成链路准备、Profile 判定和按需安全建立。

连接初始化主流程：

```
BLE 物理连接建立
  → MTU协商
  → 服务发现
  → Notify订阅 / 通道选择
  → Profile摘要查询（必要时拉取完整Profile）
  → 执行 $meta.init_pipeline
  → 业务就绪
  → 通知App设备已连接
```

#### **4.1 车机侧职责**

|  |  |
|---|---|
| 阶段 | 车机要求 |
| 服务发现 | 必须（MUST）完成 GATT 服务和特性的发现，确认 Request/Response 的可用性 |
| MTU 协商 | 必须（MUST）主动发起 MTU Exchange；若协商结果低于业务承载要求，后续消息必须走分片 |
| 通道选择 | 使用 Request/Response 的CBOR通道进行消息交互 |
| Notify 订阅 | 必须（MUST）在发送任何运行态命令前完成对应 Response 特性的 Notify订阅 |
| Profile 判定 | 必须（MUST）通过缓存或 5.4Profile 查询 确认 profile_ver、sec.sec_lvl、$meta.init_pipeline |

说明：服务发现、MTU 协商和 Notify 订阅的先后顺序可由具体 BLE 协议栈实现决定，但三者全部完成前不得进入业务初始化步骤。

#### **4.2 初始化白名单与阻塞规则**

在设备达到“业务就绪”之前，运行态流量分为两类：

**• 允许的初始化流量**：GATT 服务发现、MTU 协商、Notify 订阅、

$prof.$digest / $prof 查询、$meta.init_pipeline 声明的初始化步骤（如sec）

**• 禁止的业务流量**：除初始化白名单之外的所有业务服务读写、业务事件上报、文件传输、OTA 传输

**强制规则：**

1. 若 Profile 声明 sec.sec_lvl != "none"，或 $meta.init_pipeline 包含 "sec"，则安全握手必须（MUST）作为业务放行前的初始化步骤。

2. S1/S2/S3 设备在安全会话未建立成功前（sess_state 非 established 状态），车机和设备都禁止（MUST NOT）发送或处理非初始化业务消息；S0 设备无此限制。

3. 在初始化完成前，设备若主动上报业务事件，车机不得（MUST NOT）向上层App 透传；建议（SHOULD）设备侧也不要发送此类业务上报。

4. 任一步骤失败、超时或 BLE 断链后，车机必须（MUST）回到“未就绪”状态；若重新连接，必须从本节主流程重新开始。
