# 物模型 Profile 规范

> 来源：软件开发协议 / 直连接入协议 / 比亚迪智能设备开放接入协议 / 物模型 Profile 规范 · https://openplatform.byd.com/#/document/index?id=112

## **物模型 Profile 规范**

### **1. Profile 是什么**

**Profile 就是设备的"能力表"。**

Profile 用 JSON 格式描述设备有什么功能、每个字段是什么类型、读写权限是什么、值范围是多少。

车机拿到 Profile 后，就知道：

- 这个设备能干什么（有哪些服务）
- 每个服务有什么字段（温度、开关、模式等）
- 哪些可以读、哪些可以写、哪些会主动上报

Profile 跟设备的交互可以用"简历+对话"类比：

- Profile：简历，告诉对方"我叫什么、能干什么"
- Runtime Message：对话，实际交流"读一下温度"、"把风扇开到 3 档"

### **2. 顶层结构**

Profile 的顶层结构如下：

```
JSON
{
    "did": "000020_aabbccddeeff_ivi_BLEWifi",
    "desc": "BYD Smart Pet Cage",
    "profile_ver": "1",
    "$meta": {
    "init_pipeline": ["sec"],
    "voice_feedback": true
    },
    "srvs": {
    "dinf": { ... },
    "sec": { ... },
    "stat": { ... }
    }
}
```

|  |  |  |
|---|---|---|
| 字段 | 含义 | 说明 |
| did | 设备唯一标识 | 格式建议：<modelid>_<mac/sn>_<type>_<transport> |
| desc | 设备描述 | 人类可读的设备名称 |
| profile_ver | 物模型版本 | 用于缓存校验，避免每次连接重复拉 Profile |
| $meta | 中间件行为元数据 | 声明车机侧中间件的行为（握手阻塞、业务错误拦截等） |
| srvs | 服务集合 | 设备所有服务的定义 |

### **3. 服务定义规范**

#### **3.1 服务分类**

服务分为两类：系统服务（协议控制面）和业务服务（应用数据面）。

##### **3.1.1 系统服务（协议控制面）**

系统服务由中间件自动管理，上层 App 通常不感知。

|  |  |  |  |
|---|---|---|---|
| 服务键 | 全称 | 必选 | 说明 |
| sec | Security | 条件必选 | 安全握手/会话管理。需要加密时必须实现 |
| ftx | File Transfer | 可选 | 文件分片传输 |
| ota | OTA Upgrade | 可选 | OTA 固件升级 |

##### **3.1.2 业务服务（应用数据面）**

业务服务由上层 App 通过 AIDL 接口读写控制。

|  |  |  |  |
|---|---|---|---|
| 服务键 | 全称 | 必选 | 说明 |
| dinf | Device Information | 必须 | 设备基本信息（制造商/型号/SN/版本） |
| btry | Battery Service | 可选 | 电池电量/充电状态 |
| stat | State | 按需 | 设备运行状态属性 |
| action | Action | 按需 | 命令/动作/控制 |
| event | Event | 按需 | 事件告警上报 |
| mode | Mode | 按需 | 设备名称/模式设置 |

#### **3.2 $meta 中间件行为**

$meta 是 Profile 顶层的可选对象，告诉车机中间件该做什么，这些行为对上层 App不可见。

|  |  |  |
|---|---|---|
| 字段 | 含义 | 举例 |
| init_pipeline | 连接初始化流水线 | ["sec"] 表示安全握手完成后才通知 App 设备已连接（time_sync 等步骤定义待后续补充） |
| voice_feedback | 语音反馈通道 | true 表示 t:1 为语音TTS 反馈通道，网关拦截不上透给 App，仅触发TTS 播报 |

init_pipeline 的执行前提是：《[BLE传输层规范](#/researchTools/protocolDetail?id=111)》-4.连接初始化与业务就绪 中规定的链路准备动作已经完成。只有当 init_pipeline 中的步骤全部成功后，车机才可以将设备标记为“业务就绪”并通知 App。

若 init_pipeline 包含 "sec"，则 sec 是业务放行前的必经门禁步骤；即使handshake_mode 为 "manual"，也只是改变握手触发方，不改变“握手完成前禁止业务通信”的规则。

### **4. 字段 Schema**

每个特征字段用以下 Schema 定义：

|  |  |  |
|---|---|---|
| 字段 | 必须 | 含义 |
| f | 必须 | 数据格式标识（见第 《 编码与数据格式 》） |
| per | 必须 | 权限编码（见本文第 5 章节） |
| v | 必须 | 当前值/默认值 |
| u | 可选 | 单位（如 "℃"、"%"） |
| min/max | 可选 | 值域范围 |
| s | 可选 | 步长（如温度步进 1℃） |
| desc | 可选 | 枚举说明/描述 |

### **5. 权限编码 per**

权限用三位编码，格式为 "WRN"（从高位到低位）：

|  |  |  |
|---|---|---|
| 位 | 位置 | 含义 |
| W | bit2（高位） | Write 可写 |
| R | bit1（中位） | Read 可读 |
| N | bit0（低位） | Notify 可上报 |

常用组合：

|  |  |  |
|---|---|---|
| 编码 | 含义 | 典型场景 |
| "010" | 只读 | 设备版本号、温度（只看不改） |
| "011" | 只读+上报 | 温度（可读，设备也会主动上报变化） |
| "100" | 只写/命令 | 重置命令、发送指令 |
| "111" | 读写+上报 | 风扇模式（可读可改，设备也会上报变化） |

举例：

• "010" → 只能读，不能写，不会上报

• "011" → 可以读，设备会主动上报，但不能写（只读传感器）

• "111" → 可以读、可以写、设备也会主动上报
