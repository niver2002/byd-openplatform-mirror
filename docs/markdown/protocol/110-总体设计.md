# 总体设计

> 来源：软件开发协议 / 直连接入协议 / 比亚迪智能设备开放接入协议 / 总体设计 · https://openplatform.byd.com/#/document/index?id=110

## **总体设计**

### **1. 协议定位**

AutoIoT 协议定义为传输无关的 TSL（Thing Specification Language）物模型协议，统一解决 IoT 设备接入车机的以下问题：

• BLE 通用加密协议的安全握手

• BLE 文件分片协议的文件传输

• 各厂商数据格式的统一标准化协议包含两个核心部分：

• Profile：设备物模型定义，描述设备身份、能力、安全等级

• Runtime Message：消息交互，定义设备与车机的交互规则

协议具有传输无关特性：无论使用 BLE、CAN-FD、串口或 WiFi 传输，JSON/CBOR消息语义格式一致。厂商按 JSON 语义实现即可，无需关注底层二进制帧格式。

### **2. 设计原则**

|  |  |  |
|---|---|---|
| 原则 | 说明 | 实际场景举例 |
| 语义优先 | Profile 表达业务语义，不复刻传输层细节 | Profile 里不会出现"帧序号"这种底层概念，只有"温度"、"开关"这种业务字段 |
| 最小集合 + 扩展隔离 | Core/Domain 必须统一；厂商扩展进 ext 命名空间 | BYD 定义的 dinf、stat是核心字段；厂商自定义的功能放在 ext_xxx 里 |
| 只增不改 | 字段语义变更必须通过版本化与新字段兼容 | 如果"温度"的含义要改，不能直接改，要新增一个字段，旧字段保留两个版本周期 |
| 可跨传输 | JSON 是默认编码；CAN-FD 等可切 CBOR | BLE 用 JSON，CAN-FD用 CBOR，但语义完全一样 |
| 安全内生 | 安全不是 BLE 独占的附加层，而是物模型标准能力 | 安全握手、加密通信作为sec 服务，任何传输层都能用 |

### **3. 安全等级选择指南**

不同设备对安全的要求不同，厂商应在产品设计阶段根据实际安全需求选择对应等级：

|  |  |  |
|---|---|---|
| 等级 | 适用场景 | 安全特性 |
| S0 | 开发调试、展场演示、对安全性无要求的低成本设备 | 无加密、无认证 |
| S1 | 部分 BLE 可车控设备（已在部分 BLE 可车控设备中安排使用） | 加密通道 + 临时签名，无长期身份认证 |
| S2 | 高风险设备（门锁、支付设备） | 后端验证身份后，再建立 S1 级加密通道 |
| S3 | 特殊场景（厂商自有云端认证等） | 自定义验证 + ECDH 加密 通道 |

等级从 S0 到 S3 安全强度递增。建议不确定时先选用 S1，后续可根据安全需求升级至 S2。

|  |  |  |  |
|---|---|---|---|
| 等级 | 标识 | 适用场景 | 厂商开发要点 |
| S0 | none | 调试、开发板、展示样品 | 不需要声明 sec 服务 |
| S1 | ecdh_only | 部分 BLE 可车控设备 | 实现临时密钥对生成 + AES-GCM 加密；详见《AutoIoT 安全服务技术实现》 |
| S2 | ecdh_auth | 高安全场景（门锁、支付设备） | 需要长期密钥对（出厂烧录）+ 后端注册；详见《AutoIoT 安全服务技术实现》 |
| S3 | custom_auth | 特殊场景（厂商自有云端认证） | 与 BYD 协定自定义验证方案；详见《AutoIoT 安全服务技术实现》 |
