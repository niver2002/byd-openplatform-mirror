# 消息交互规范

> 来源：软件开发协议 / 直连接入协议 / 比亚迪智能设备开放接入协议 / 消息交互规范 · https://openplatform.byd.com/#/document/index?id=113

## **消息交互规范**

### **1. 消息结构 Envelope**

设备与车机的交互消息采用统一的 Envelope 结构承载：

```
JSON
{
    "mid": "123",
    "op": "r",
    "srv": "stat",
    "chr": "temp_cage",
    "v": "25",
    "code": 0,
    "err": [],
    "msg": ""
}
```

|  |  |  |
|---|---|---|
| 字段 | 含义 | 必须 |
| mid | 消息 ID（请求和响应配对） | req/rsp 必须 |
| op | 操作类型：r=读, w=写,n=上报 | 必须 |
| srv | 服务键 | 必须 |
| chr | 特征键 | 必须 |
| v | 值（简单读写时使用） | 按需 |
| in | 命令入参（复杂命令时使用） | 按需 |
| out | 响应出参/事件出参 | 按需 |
| code | 响应状态：0=成功，-1=失败 | rsp 必须 |
| err | TLV 错误数组（失败时返回） | 错误时必须 |
| msg | 错误描述（可选） | 可选 |

### **2. 操作语义 r/w/n**

#### **2.1 读特征 op:"r"**

用于车机读取设备字段值。

```
请求 → {"mid": "1", "op": "r", "srv": "stat", "chr":"temp_cage"}
响应 ← {"mid": "1", "code": 0, "v": "25"}
```

#### **2.2 写特征 op:"w"**

**简单值**写入（如设置风扇档位）：

```
请求 → {"mid": "2", "op": "w", "srv": "dinf", "chr": "new_name", "v": "新名字"}
响应 ← {"mid": "2", "code": 0}
通知数值变化 ← { "op": "n", "srv": "dinf", "chr": "new_name", "v": "新名字"}
// 异常举例 值相同时，如下返回 ，供其他模块使用
{"mid": "2", "code": -1, "err": [{"t": 1, "v": "3"}]}
```

**复杂命令**写入（如重置设备）：

```
请求 → {"mid": "3", "op": "w", "srv": "action", "chr":"factory_reset", "in": {"confirm": "1"}}
响应 ← {"mid": "3", "code": 0, "out": {"accepted": "1"}}
```

**注意**：v 和 in 互斥，一个消息里不能同时出现。

#### **2.3 事件上报 op:"n"**

用于设备主动上报状态变化或告警信息。

```
设备→车机: {"op": "n", "srv": "event", "chr": "fault_code","out": {"code": "E001"}}
```

事件上报没有 mid（或可选），因为是设备主动发起，不需要配对响应。

### **3 批量操作**

当需要同时读取或写入多个字段时，逐个操作效率较低。批量操作可一次完成多个读写请求，提高交互效率。

批量读：

```
请求 → {"mid": "5", "op": "r", "srv": "stat", "chr":["fan_mode", "cage_switch", "temp_cage"]}
响应 ← {"mid": "5", "code": 0, "v": {"fan_mode": "3","cage_switch": "1", "temp_cage": "25"}}
```

批量写：

```
请求 → {"mid": "6", "op": "w", "srv": "stat", "v":{"fan_mode": "3", "cage_switch": "1"}}
响应 ← {"mid": "6", "code": 0}
```

### **4. Profile 查询**

Profile 可能较大（几十 KB），每次连接完整拉取会浪费带宽。因此采用摘要查询机制：先查询 Profile 摘要，若与本地缓存版本一致则无需重新拉取完整 Profile。

摘要用于连接初始化阶段的快速判定，返回的是“值摘要”，不是完整 Profile Schema。因此摘要字段不携带 f / per / v 包装；完整字段类型、权限、默认值仍以完整 Profile为准。

摘要查询：

```
请求 → {"mid": "10", "op": "r", "srv": "$prof", "chr":"$digest"}
响应 ← {
    "mid": "10",
    "code": 0,
    "v": {
        "profile_ver": "1",
        "sec": {
            "sec_lvl": "ecdh_auth",
            "suites": ["A256GCM"],
            "preferred_suite": "A256GCM",
            "handshake_mode": "auto",
            "backend_policy": "strict"
        },
        "init_pipeline": ["sec"]
    }
}
```

|  |  |  |
|---|---|---|
| 摘要字段 | 必须 | 说明 |
| profile_ver | 是 | Profile 版本，用于缓存兼容性判断 |
| profile_hash | 建议 | 完整 Profile 内容哈希；若与缓存一致，可复用本地完整 Profile |
| sec | 条件 | 安全能力摘要；设备需要安全握手或支持安全服务时返回 |
| sec.sec_lvl | 条件 | 安全等级：none /ecdh_only /ecdh_auth /custom_auth |
| sec.suites | 条件 | 设备支持的安全套件列表，按设备偏好排序 |
| sec.preferred_suite | 条件 | 设备推荐套件；车机不支持时可从 suites 中选择其他共同支持套件 |
| sec.handshake_mode | 条件 | auto / manual，含义同完整 Profile |
| sec.backend_policy | 条件 | S2 后端不可达策略，含义同完整 Profile |
| init_pipeline | 建议 | 连接初始化流水线摘要，用于快速决定初始化步骤 |

sec.suites 使用短码，仅表达业务载荷保护算法；握手等级和认证方式由

sec.sec_lvl 决定。P-256 ECDH、ECDSA SHA-256、HKDF-SHA256 等基础密码参数见《AutoIoT 安全服务技术实现》。

**摘要一致性规则：**

1. 车机可仅通过$prof.$digest 完成连接初期的安全能力判定；若profile_hash 与本地缓存一致，可复用本地完整 Profile。

2. 若无本地缓存、profile_hash 变化、摘要缺少必要安全字段，车机必须（MUST）拉取完整 Profile。

3. 若摘要中的 sec 或 init_pipeline 与完整 Profile 不一致，车机必须

（MUST）以完整 Profile 为准，并建议终止本次初始化后重新执行连接初始化流程。4. 摘要中的 sec.suites 只表达设备能力，不表示最终选择结果；最终使用的套件由车机在 sec.init.selected_suite 中声明。

**仅支持遗留 AES-ECB-128 设备的摘要示例**：

```
JSON
{
    "profile_ver": "1",
    "profile_hash": "sha256:8e7a1f2c9b0d4a6e",
    "sec": {
        "sec_lvl": "ecdh_auth",
        "suites": ["A128ECB"],
        "preferred_suite": "A128ECB",
        "handshake_mode": "auto",
        "backend_policy": "strict"
    },
    "init_pipeline": ["sec"]
}
```

A128ECB 仅用于遗留兼容，不建议新设备使用；该套件的业务加密封装、完整性保护要求见《AutoIoT 安全服务技术实现》。

完整 Profile 查询：

```
请求 → {"mid": "11", "op": "r", "srv": "$prof"}响应 ← {"mid": "11", "code": 0, "v": { ...完整ProfileJSON... }}
```

如果 Profile 超过 MTU，会自动启用分片机制。
