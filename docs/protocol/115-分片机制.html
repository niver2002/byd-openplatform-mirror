分片机制

来源：软件开发协议 / 直连接入协议 / 比亚迪智能设备开放接入协议 / 分片机制 · 文档 ID 115 · 原始页面

分片机制

1. 物模型完整查询信封（分片前示例）

分片传输前，发送端先将完整业务信封编码为字节流，再按 MTU 拆分。以下以物模型查询为例展示分片前的完整信封结构，同时给出 JSON 和 CBOR 两种表示。

请求（车机→设备）

JSON 表示：

JSON
{"mid": "3", "op": "r", "srv": "$prof", "chr": "all"}

CBOR 数据结构（DevTools 风格树）：

Plain Text
▼ map {5}            ~15B
mid : text "3"        2B
op : text "r"         2B
srv : text "$prof"    6B
chr : text "all"      5B

响应 （设备→车机）

注意，后面分片是把整个如下的内容 json 转换后的 cbor 进行分片JSON 表示：

JSON 表示：

JSON
{
    "mid": "3",
    "op": "r",
    "srv": "$prof",
    "chr": "all",
    "code": 0,
    "v": { ... } // 完整物模型 JSON 结构
}

CBOR 数据结构：

Plain Text
▼ map {6}            ~XXXB
mid : text "3"        2B
op : text "r"         2B
srv : text "$prof"    6B
chr : text "all"      5B
code : uint 0         1B
▼ v : map {2}        ~XXKB
    ↑ 物模型数据(CBOR-native Map, 不是 JSON 字符串)
    ↑ 整个信封编码为 CBOR 字节流后 → 分片传输 → 重组后还原此完整结构

CBOR 关键点：

  • op 为 text string "r"，不是整数
  • v 为 CBOR-native 结构（Map/Array），不是嵌套的 JSON 字符串
  • 整个信封编码为一个 CBOR Map 字节流 → 按 max_frag_size 拆分 → 每片raw 承载一个 chunk
  • 重组后 CBOR 解码还原完整信封，所有原始字段（mid/op/srv/chr/code/v）完整保留

2. 分片触发条件

单条消息超过 MTU 时需拆分传输。常见场景包括：

• Profile 查询响应（可能几十 KB）

• 大型加密业务消息

3. 分片消息格式

JSON 表示：

JSON
{
    "mid": "400",// 递增
    "$frag": {
        "frag_id": "3",  // 使用拆分前完整数据包的mid(§7.0 业务信封的 mid)
        "frag_idx": 0,   // 不同分片递增
        "frag_cnt": 3,
        "crc": 48674
    },
    "raw": "eyJtaWQiOjQwMCwib3AiOiJyIiwic3J2Ijoi..."
}

CBOR 数据结构（DevTools 风格树）：

Plain Text
▼ map {3}                   ~XXB
mid : text "400"            5B
▼ $frag : map {4}           ~XXB
    frag_id : text "400"    5B
    frag_idx : uint 0       1B
    frag_cnt : uint 3       1B
    crc : uint 48674        3B
raw : byte string           ~XXB
    hex h'6da56d69645f3f7e8a...'    (完整信封 CBOR 编码的第 0个 chunk)

说明：raw 字段承载的是本文1章节 中完整信封经过 CBOR/JSON 编码后字节流的一个分片，而非业务数据本身。JSON 传输下为 base64 字符串；CBOR 传输下为 bytestring。

字段含义
frag_id分片组ID（等于拆分前完整数据包的mid，即本文1章节 业务信封的 mid）
frag_idx当前片索引（从 0 开始）
frag_cnt总片数
crc当前片的 CRC-16 校验（CRC-16/MODBUS，多项式 0xA001，初值 0xFFFF）
raw完整信封编码字节流的一个分片。发送端先将完整业务信封（含 mid/op/srv/chr/v等所有字段）编码为 CBOR或 JSON 字节流，再将该字节流按 max_frag_size 拆分，每片的 raw 承载一个分片。JSON 传输下分片为base64 编码；CBOR 传输下分片为 byte string。重组后解码可还原完整信封的所有原始字段，而非仅业务数据。

外层字段约束：分片帧外层只保留 mid、$frag、raw 三个字段；原始消息的op、srv、chr、v/in/out 都被编码进 raw 内部，不再重复出现在外层。ACK帧外层只保留 mid、$frag 两个字段（ACK 无 raw、无 op/srv/chr/code 等业务字段，无 frag_cnt）。

mid 与 frag_id 的关系：

规则说明
每片独立 mid每个分片帧拥有自己的 mid，用于与对应 ACK 一一匹配
frag_id = 原始完整数据包的 midfrag_id 固定等于拆分前业务信封（第1章节）的 mid。
frag_id 全组不变同组所有片和所有 ACK 的 frag_id 都保持一致
ACK 的 midACK 的 mid 等于其确认的那一片的 mid （非 frag_id）

3. 分片确认与重传

每片传输后，接收端返回 ACK：

JSON 表示：

JSON
{"mid": "401", "$frag": {"frag_id": "3", "frag_idx": 1,"result": 0, "next": 2}}

CBOR 数据结构（DevTools 风格树）：

Plain Text
▼ map {2}               ~XXB
mid : text "401"        5B ← 等于被确认的那一片(fragIdx=1)的 mid
▼ $frag : map {4}       ~XXB
frag_id : text "400"    5B ← 全组不变=首片 mid
frag_idx : uint 1       1B ← 确认的片索引
result : uint 0         1B ← 0=成功
next : uint 2           1B ← 建议下一片索引 (最后一片=-1)

最后一片 ACK 示例（fragIdx=2, fragCnt=3, next=-1）：

Plain Text
▼ map {2}               ~XXB
mid : text "403"        5B ← 等于被确认的最后一片(fragIdx=2)的 mid
▼ $frag : map {4}       ~XXB
frag_id : text "3"    5B
frag_idx : uint 2       1B ← 最后一片
result : uint 2         1B
next : nint -1          1B ← -1 表示所有分片已收齐

ACK 字段约束：mid 等于被确认的那一片的 mid（非独立生成，非固定值）。$frag 仅含 frag_id、frag_idx、result、next，不含 frag_cnt。

result值含义next处理方式
0成功(中间片)frag_idx+1发送下一片
1请重传frag_idx(当前片)重发当前片（最多3次）
2终止/完成-1停止发送(含最后一片正常完成 和 CRC重传超限异常终止)

最后一片的 ACK：当 frag_idx == frag_cnt - 1（最后一片）时，ACK 的next 字段为 -1，表示所有分片已收齐。其余片的 ACK next 为建议的下一片索引（frag_idx + 1）。

重传策略：收到 result=1 时重发当前片，重试次数超过 3 次则放弃本次传输。

超时机制：接收端对每个分片组（fragId）维护 5 秒超时计时器：若 5 秒内未收到同一fragId 的下一个分片，则丢弃该 fragId 的重组缓冲区。超时后若收到 fragIdx=0 的分片，开始新的重组；若收到非零 fragIdx 的分片，视为无效丢弃（缺少首片无法重建）。

处理顺序与嵌套规则：

• 发送端：原始业务消息 → $sec 加密（如启用）→ $frag 分片 → 传输层

• 接收端：传输层 → $frag 重组 → $sec 解密（如启用）→ 业务处理

• $frag 必须位于最外层，禁止 $frag 内再嵌套 $frag

• $sec 总是针对完整业务消息加密，而不是对单片分别加密
